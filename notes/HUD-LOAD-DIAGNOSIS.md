## Existing evidence and scope

0.1.10 already fixes the A7 16KiB-task/4KiB-kernel-page mismatch. The previous
same-source native read is 576.64MiB used /975.96MiB physical, including inactive
pages. The reported ~600MiB is not presumed erroneous. HOST_VM_INFO active,
inactive and wired counts are system allocation categories, not summed app RSS
or a direct memory-pressure measurement. Speculative pages are already included
in free_count; purgeable pages overlap existing queues and must not be added
as a separate total. Source: Apple XNU2422 vm_statistics.h:
https://github.com/apple-oss-distributions/xnu/blob/xnu-2422.1.72/osfmk/mach/vm_statistics.h

GPUUtilization reads the bounded driver percentage directly; it does not derive
a percentage from a cumulative counter. The driver sampling interval/freshness
is not established merely by the name. Global GPU readings cannot by themselves
identify a process. Process CPU is supporting evidence, not GPU attribution.

Call sites inspected: GPUUtilization/MemoryUsage → visible PerfOverlay tick;
native-metrics.m reuses those exact functions. Hidden HUD stops its timer and
pauses its display link. With the global counter working the display link is
paused even when shown. Each visible timer tick replaces label text, relayouts
the panel and writes an existing diagnostic log; observer overhead requires A/B.

## Controlled native results

Installed0.1.10, iPad4,5/iOS7.1.2, native arm64. Parent supplied an exclusive
post-reboot UI window. Initial screen was locked without passcode, HUD Enabled
true. The existing guarded device-access adapter unlocked it; the existing
entitled Launch helper selected Home or Settings. Visibility changed only via
PerfOverlay's existing Darwin notification and SpringBoard handler. No service
was killed, paused, disabled or reconfigured; no package installed or respring.

Each main run captured20 samples at1s, after5s settling (first Home ON included
the unlock transition). Summary discards the first3 records, retaining~16s.
The sole observer remained identical across ON/OFF windows.

These are actual driver snapshots. The product does not multiply/scale the
percentage and does not treat a cumulative counter as a percent. Per-sample
CommandBufferRenderCount was approximately10 on Home OFF,5 on Settings ON,
and0 on settled Settings OFF. Driver values returned to zero when rendering
stopped, so this run does not support a permanently stale30–40% display.
The source already rejects absent/non-number/out-of-range values.

Causal conclusion: Settings idle GPU load is generated by observing it with a
live composited HUD. Home has additional foreground/compositor work visible
even without HUD. The exact Home animation/content was not isolated; do not
claim live wallpaper, parallax, clock or a background daemon as a proven cause.
Global AGX data exposes no per-process GPU attribution here. Process CPU ranks
are not evidence assigning the GPU percent to a process. Hardware clock/DVFS
and the driver's exact percentage averaging interval were not calibrated, so
30% must not be presented as30% of peak GPU power/performance or battery watts.
